[2] SECURITY RULES (RESUMEN LÓGICA CRÍTICA)

- isAdmin(): request.auth.token.role == "admin"
- isPartner(): request.auth.token.role == "partner"
- isValidDevice(): request.auth.token.deviceId == user.deviceId
- isNotRevoked(): !user.isRevoked

- memories: Partner lee todo EXCEPTO adminNotes (filtrado client + rules). Partner solo update isSpecial/partnerNote. Admin update todo.
- capsules: Partner solo lee si isUnlocked==true && isDestructed==false.
- bingoBoard: Partner solo puede marcar completado (no desmarcar). Admin control total.
- coupons: Partner lee activos. Admin CRUD total.
- activityLog: Partner crea (sus acciones). Admin lee todo.

[5] AUTH FLOW (PARTNER)

1. Admin genera inviteToken -> URL con token.
2. Partner abre URL -> App genera deviceFingerprint (localStorage).
3. App llama exchangeInviteToken(token, fingerprint).
4. CF valida -> Crea user en Firestore -> Genera Custom Token con claims {role, deviceId}.
5. App signInWithCustomToken -> Persistencia en IndexedDB.
6. Revocación: Admin set isRevoked=true -> Security Rules bloquean acceso.

[6] OFFLINE-FIRST ARCHITECTURE

- Hook: useOfflineQueue (gestiona estado local).
- Storage: IndexedDB (AppDB) -> Store: uploadQueue.
- Sync: Service Worker (background sync event).
- Logic: Queue FIFO -> Sube 1 foto cada 3s -> Retry 3x con backoff -> Notificación éxito/fallo.
- Limites: Max 100MB o 50 items en queue.
